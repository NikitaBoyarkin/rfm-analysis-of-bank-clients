# A/B Test Results: EXP-001 Win-back (At Risk + Hibernating)

**Гипотеза:** персонализированный win-back оффер (кэшбэк 5% на 3 транзакции) повышает 30-дневную реактивацию At Risk + Hibernating на ≥3 п.п. (с 6% до 9%).
**Длительность (план):** 44 дня (30 дней окна + 14 дней хвоста) | **Выборка (план):** 496 control / 496 test из 992 eligible.
**Статус:** readout невозможен — данных о назначении и реактивации нет. Проведён аудит дизайна.

## Главный вывод

Рекомендация по дизайну: **Investigate** — в текущем виде тест не способен подтвердить собственную гипотезу.
При 496 клиентах на плечо мощность для заявленного эффекта +3 п.п. равна **0.44** (нужно ≈1207/плечо).
Минимальный детектируемый эффект при 80% мощности — **4.93 п.п.**, то есть тест видит только эффект почти вдвое больше заявленного.

## Калибровка базовой ставки (p₁)

Документ берёт p₁ = 0.06 как «historical baseline estimate», но в репозитории нет источника. Проверка по транзакциям: сегментация пересчитана на более раннюю дату (2023-12-31), затем измерена доля eligible-клиентов с ≥1 транзакцией в следующие 30 дней.

| Сегмент | n | Реактивировались за 30 дн. | Ставка |
|---|---|---|---|
| At Risk | 366 | 88 | 24.0% |
| Hibernating | 617 | 162 | 26.3% |
| **Итого** | **983** | **250** | **25.4%** (95% CI 22.8–28.2%) |

**Как читать:** 25.4% — свойство генератора (`generate_data.py`, равномерные даты транзакций), а не банка. Это не оценка p₁ для продакшена. Но вывод от этого только усиливается: 6% ничем в репозитории не подтверждены, а мощность теста критически зависит от базы.

| p₁ | Нужно n/плечо для +3 п.п. | Мощность при 496/плечо | MDE при 80% мощности |
|---|---|---|---|
| 0.02 | 586 | 0.73 | 3.33 п.п. |
| 0.03 | 746 | 0.63 | 3.83 п.п. |
| 0.05 | 1 057 | 0.48 | 4.61 п.п. |
| 0.06 (документ) | 1 207 | 0.44 | 4.93 п.п. |
| 0.10 | 1 772 | 0.32 | 5.95 п.п. |
| 0.15 | 2 400 | 0.25 | 6.87 п.п. |
| 0.25 (replay) | 3 394 | 0.19 | 8.04 п.п. |

Доступные 496/плечо хватают заявленный эффект только при p₁ ≤ ≈1.3% — то есть при базе, которой у At Risk + Hibernating быть не может по определению сегментов.

## Guardrail-метрики

| Guardrail | Порог | Проверка | Статус |
|---|---|---|---|
| Unsubscribe / complaint rate | ≤0.6% | 0.4% baseline, n=496 на плечо — для детекции роста до 0.6% мощности нет | ⚠️ направленный, не блокирующий |
| Cost per reactivated | ≤600 ₽ | средний чек eligible = 3 030 ₽ → 5% × 3 × 3 030 ≈ 455 ₽ | ✅ реализуемо, запас ~24% (пробой при чеке >4 000 ₽) |
| Churn Champions/Loyal (counter) | без изменений | сегмент не в эксперименте; метрика ловит spill-over, но без holdout эффект не отделить от сезонности | ⚠️ механизм не задан |

## Рекомендация

**Investigate — не запускать как confirmatory тест на 992 клиентах.**

Что сделать до запуска:

1. **Взять p₁ из истории кампаний**, а не из оценки. Если реальная база ≥5% — 496/плечо недостаточно, нужно ≥1 100/плечо.
2. **Выбрать один из двух режимов и записать его в дизайн:**
   - *exploratory pilot*: pre-registered MDE = 5 п.п., отчёт как «направленный сигнал», не как подтверждение;
   - *confirmatory*: расширить популяцию (At Risk + Hibernating + Need Attention = 1 402) и/или удлинить окно до 60 дней, пере-пауэрить.
3. **Pre-register decision rule** для случая «primary не значим, guardrails чистые» — сейчас правило есть только для значимых исходов.
4. **Зафиксировать статус подгрупп:** At Risk и Hibernating анализировать как exploratory (в replay ставки близки — 24.0% vs 26.3%, но на реальных данных расхождение может быть кратно больше).
5. **Добавить exposure-логирование** (кому доставлено, когда открыто) — без него нельзя отличить «оффер не сработал» от «оффер не дошёл».

## Как посчитать readout, когда данные появятся

```bash
python scripts/ab_test_analyzer.py --results data/exp001_results.csv
```

Обязательные колонки: `customer_id`, `variant` (control|test), `converted` (0/1). Опционально: `revenue_30d`, `unsubscribed`, `offer_cost` — тогда считаются guardrails с Holm-поправкой и Welch-тест по выручке, а рекомендация формируется автоматически.

```bash
python scripts/ab_test_analyzer.py --design        # аудит плана
python scripts/ab_test_analyzer.py --sensitivity   # мощность по сетке p₁
python scripts/ab_test_analyzer.py --baseline      # replays-оценка базы
```
